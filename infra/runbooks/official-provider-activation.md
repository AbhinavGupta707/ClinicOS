# Official Provider Activation Runbook

This runbook governs CP15 Meta WhatsApp Cloud and Razorpay activation. It does not authorize an
AWS/DNS deployment, provider-dashboard change, message send, payment creation, or use of clinic or
patient data. ClinicOS currently remains under the owner-approved cloud deferral in
`docs/orchestration/CHECKPOINT_14_CLOUD_DEFERRAL_DECISION.md`; the local implementation must stay
disabled until every applicable precondition below is independently satisfied.

Telephony is not selected or registered. Its workflow remains absent/disabled and must not be
approximated with a generic webhook, browser automation, or simulator presented as provider truth.

## Activation authority and separation of duties

The release owner authorizes the environment and spend. A provider administrator registers the
callback and event subscriptions. A secrets operator creates or rotates values in the approved
secret manager. A database operator writes only opaque registration identifiers and secret ARNs.
An independent reviewer verifies the resulting provider state and evidence. No one records secret
values, callback registration keys, tokens, message content, patient identifiers, or payment
payloads in tickets, shell history, screenshots, logs, or this repository.

Use a synthetic provider test account and synthetic clinic scope for E4 evidence. Live mode and real
clinic data require the later release/governance gates.

## Preconditions

1. The exact reviewed application image and migrations `0020`/`0021` are deployed behind a stable HTTPS
   origin with valid TLS, edge rate controls, restricted raw-body S3/KMS storage, runtime and worker
   roles, telemetry, alert delivery, and rollback capability.
2. `CLINIC_OS_OFFICIAL_PROVIDER_CALLBACKS_ENABLED=true` is accepted only when the endpoint-HMAC,
   restricted webhook bucket/prefix/KMS key, AWS region and database role settings all pass startup.
3. The provider account, mode, Meta API version/WhatsApp business and phone-number identifiers, or
   Razorpay account identifier are independently verified. Approved Meta templates and documented
   patient consent/opt-out behavior exist before any send.
4. Current secrets exist in AWS Secrets Manager. PostgreSQL receives only full Secrets Manager ARNs;
   migration constraints reject raw secret values and unsupported references.
5. A 32-byte-or-stronger opaque callback registration key is generated by a cryptographic random
   source. The external URL contains that one-time-delivered value, while PostgreSQL stores only its
   lowercase SHA-256 digest. The key is not an authentication substitute; signatures remain
   mandatory.

## Atomic registration

Registration is an audited privileged operation, not a public product API. In one transaction under
the intended tenant and clinic scope, the operator must:

1. lock and verify exactly one matching `external_accounts` row and its provider capability set;
2. insert or compare-and-swap one `provider_callback_registrations` row with provider/account/mode,
   endpoint/API identifiers, callback-key digest, secret ARNs and current secret version;
3. begin at `registered` or `configured`—never `sandbox_verified` or `production_verified` without
   the corresponding evidence;
4. let the database trigger maintain the forced-RLS opaque `provider_callback_routes` index;
5. append a PHI-free administrative audit event and outbox event; and
6. commit only if the expected row version and all invariants still match.

Direct reads or writes to `provider_callback_routes` are forbidden. Runtime and worker roles are
explicitly denied access; public resolution uses only the bounded security-definer resolver.

## Provider registration

### Meta WhatsApp Cloud

- Register both GET challenge and POST events at
  `https://<approved-origin>/v1/provider-callbacks/meta-whatsapp/<opaque-registration-key>`.
- Resolve the verification token from its secret ARN and complete the official challenge. Subscribe
  only to reviewed WhatsApp message/status events for the bound business and phone-number IDs.
- Prove invalid challenge and invalid `x-hub-signature-256` rejection, signature-before-parse,
  duplicate replay, delayed/out-of-order statuses, opt-out/consent, template/service-window rules,
  provider outage and bounded retry/manual-review behavior.
- A send request proves only provider acceptance. Only verified callback evidence may advance
  sent/delivered/read state.

### Razorpay

- Register POST events at
  `https://<approved-origin>/v1/provider-callbacks/razorpay/<opaque-registration-key>` for the exact
  test account and reviewed payment/refund/dispute event set.
- Prove invalid signature rejection before parsing, event-ID replay, partial and duplicate payment,
  out-of-order events, amount/currency/invoice mismatch, overpayment, refund/dispute, outage and
  reconciliation recovery.
- Client redirects, API creation responses and reconciliation reads never mark an invoice paid.
  Settlement requires a verified signed event and the canonical atomic billing transaction.

## Secret and callback-key rotation

1. Create a new secret version and update the registration with expected-row-version protection.
2. Retain the previous webhook secret ARN/version only for a short, explicit
   `previous_secret_accept_until` overlap. Verify both paths with synthetic events.
3. Remove the previous reference immediately after the window and confirm old signatures fail.
4. Callback-key rotation creates a new opaque key/digest and atomically updates the route index;
   update the provider dashboard, verify the new route, then remove the old provider registration.
5. Record operator, reviewer, environment, provider account, versions and timestamps without values.

## Monitoring, reconciliation and recovery

- Use the authenticated provider operations view and `/v1/provider-health`; neither returns secret
  references. Alert only when a provider is expected live in that environment.
- Reconciliation workers claim due jobs with bounded leases and tenant/clinic RLS, and finalize job
  plus provider health atomically. Razorpay may use bounded official read-only evidence. Meta status
  uncertainty remains manual review because no general authoritative status lookup is assumed.
- Never bulk replay without reviewing scope and idempotency. A replay request does not prove an
  external side effect or provider-confirmed state.
- On invalid-signature spikes, credential failure, scope conflict or payment variance, degrade or
  disable the registration, preserve evidence, stop new side effects where required and follow
  `provider-health-alerting.md`.

## Rollback

Disable the registration with compare-and-swap, stop new sends/payment requests, remove or disable
the provider dashboard callback, retain audit/raw/reconciliation evidence according to policy, and
confirm the public callback returns a bounded unavailable/not-found response without exposing
registration state. Do not delete evidence or rewrite provider-confirmed history. Re-enable only
after a new independent verification pass.

## Required evidence

Capture the exact commit/image digest, environment and provider test account; redacted dashboard
registration; TLS/callback URL; challenge/signature, duplicate/order/retry/outage/reconciliation
results; health and alert delivery; current/previous rotation behavior; tenant-negative checks;
audit/outbox correlation; and rollback/re-enable results. Official sandbox evidence is E4. Local
fixtures, deterministic contract tests and the clean-database persistence proof remain E1-E3 and
must never be relabelled as provider activation.
